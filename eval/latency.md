# 服务延迟实测（2026-11-23）

两档同一方法（`tools/d6_latency.py`，并发 4、热态 120 样本、预热 15 次单独留档）。
**形态/后端一律取自 `/healthz` 实测**，⛔ 写死在报告模板里。

| 形态 | trace 后端 | P50 | **P95** | P99 | 冷启动 P95 |
|---|---|---|---|---|---|
| 本机单实例 uvicorn | sqlite | 52.0 ms | **73.7 ms** | 88.2 ms | 655.1 ms |
| compose 容器（app+postgres+qdrant） | postgres | 60.9 ms | **77.9 ms** | 104.4 ms | 638.5 ms |

- 容器相对本机 P95 约 **+4 ms**（Postgres 往返 + 容器网络），量级合理。
- 冷启动 ≈ **0.64 s**：首批请求要建数据集与首次导入，所以 P99 明显抬高。
  两栏**分开留档**：冷启动值⛔ 被抹掉，也⛔ 混进热态数。

## 两个被自己抓出来的测量错误（留着，⛔ 假装没发生）

1. **形态标签硬写**：第一版报告里写死「容器 = 否」，而那次测的正是 compose 起的容器
   ⇒ 标签改为从 `--external` 与 `/healthz` 推导。
2. **"冷启动"其实不冷**：第一次容器测的预热样本 P95 只有 68 ms——因为我在测之前
   已经用冒烟脚本打过请求，数据集早建好了。⇒ 改成 `docker compose restart app` 后
   **立刻**采样，才拿到 638.5 ms 这个和本机同量级的真值。

⚠️ 引用任何 P95 必须带上「形态 + 并发 + 样本量 + 后端」。这里测的是**单机、无鉴权、
无网络跳数**，容器那档也只到"单机 compose"，⛔ 等于集群容量规划。
